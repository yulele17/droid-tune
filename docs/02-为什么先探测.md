# 02 · 为什么必须先探测

这是本项目的核心，也是它存在的理由。如果你只看一篇文档，看这篇。

## 一次真实的全军覆没

设备：Redmi Note 13 Pro（2312DRA50C），国行 HyperOS 3，ROM 版本 `OS3.0.306.0.WNRCNXM`。

流程非常标准：拿 UAD-ng 官方 debloat 清单，和手机上真实安装的 475 个包做交叉比对，
筛出 55 个既被官方点名、又确实装在这台机器上的候选包，逐个执行：

```bash
adb shell pm disable-user --user 0 com.miui.analytics
adb shell pm disable-user --user 0 com.miui.daemon
...
```

结果：

```
成功冻结   7 个
系统拒绝  48 个
失败率    87%
```

拒绝信息统一是这一句：

```
Exception occurred while executing 'disable-user':
java.lang.SecurityException: Cannot disable system packages
```

被拒的清单包括 `com.miui.analytics`（小米自家遥测）、`com.miui.daemon`、`com.miui.uireporter`、
`com.miui.yellowpage`、以及全部 overlay 包 —— 也就是 UAD 清单里**最重点**要处理的那批。

## 这意味着什么

**ROM 层面把"自家的遥测/广告/overlay 包"标成了不可禁用的系统核心包。**

`pm disable-user` 是 Android 官方接口，但厂商有权对自己的预装施加更强的保护。
adb 工具在它面前没有任何特权。

更麻烦的一点：**没有任何工具会提前告诉你这件事**。它们的做法是照着清单往下跑，
跑完甩给你 48 行红色报错，让你自己去猜：

- 是包名拼错了？
- 是 adb 版本不对？
- 是设备没连好？
- 还是这台机器本来就不行？

正确答案是最后一种，但你要花很久才能确认。

## 本项目的解法：probe

与其事后浪费 48 次尝试，不如**事前来一次低成本、完全可逆的试探**。

`probe` 的做法：

1. 从 UAD 候选清单里挑少量探针包（默认 6 个，全都是应用类，不是系统核心）；
2. 对每个包执行一次 `disable-user`；
3. **立刻执行 `enable` 把它恢复原状**；
4. 记录系统返回的是"允许"还是"拒绝"。

全程无副作用，结束时设备状态和探测前一致。然后根据"允许禁用比例"分流：

| 允许比例 | 结论 | 建议路线 |
|---|---|---|
| ≥ 60% | debloat 路线可行 | 正常 `plan` → `freeze` |
| 20% ~ 60% | 部分可行 | 可以做，但要预期大量报错；剩余的改用 UI 路线 |
| < 20% | 基本不可行 | **别冻了**，改走 uiautomator2 模拟点设置开关 |

## 不可行时该走哪条路

如果一个 ROM 不让你禁用它的包，还有一条完全不同的路：
**不去动包，而是通过模拟点击去关掉 App 内部的开关。**

典型代表是 [android-ad-cleaner](https://github.com/rddmwmddr/android-ad-cleaner)——
它用 uiautomator2 读取屏幕、找到「个性化广告推荐」这类开关并关掉，
全程不和 `pm disable` 打交道，所以不受上面的限制。

这也解释了为什么那类工具要写得那么"重"（依赖 uiautomator2、要读屏、要判机型）：
厂商在 ROM 层面堵死了包管理的路，只能在 UI 层绕。

两条路的关系：

```
                    ┌─ 允许禁用 → pm disable-user（droid-tune freeze）
probe 探测这台 ROM ──┤
                    └─ 拒绝禁用 → UI 模拟点击（android-ad-cleaner）
```

## 所以请养成一个习惯

**换任何一台新机器，先把 `probe` 跑一遍。** 十几秒钟的事情，
能省掉几十次注定失败的尝试，更重要的是——让你从一开始就对这台机器的实际状况有数。

```bash
python -m tune probe --save
```
